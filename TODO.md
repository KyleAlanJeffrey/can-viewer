- [x] Open another log, or cancel, while a log is read: the app disables its open controls and turns dropped or picked files away while busy, and `serially` queues every open behind the last, so it never sends the core a second `openLog` to supersede the first. Letting it would also need `openLog` in `App.tsx` to ignore the old call's `AbortError` (not show it, and not clear the newer log). While a log is read, Open Log..., a dropped log and Try the Demo now read the new log in its place, and a Cancel button in the toolbar, before Open Log..., stops the read. Each read is marked stopped and the core is sent an empty log (it has no cancel), so the read ends as soon as the core can; a stopped read leaves the UI to whatever replaced it, and its progress and `AbortError` are ignored. The core freed the log shown before when the read began, so Cancel reads it again from its saved copy, with the UI it had, or leaves no log and forgets the saved copies when there is none; a log that fails to open puts the log shown before back the same way, its error still shown, and only a reopen that fails leaves no log and forgets the copies, so a reload never brings back a log the UI no longer shows and a bad copy can't loop. Capture... (which would supersede the read too, but needs Cancel first), log B, DBCs alone and the other busy tasks are still turned away while busy
- [x] Parsing in one worker: `IdIndex::observe` took about 88 ns per frame natively, about a third of a candump frame's load; it now takes about 20 ns. Bit flips are added up in eight byte-wide counters per payload byte (`FlipTally` in `crates/can-core/src/store/flips.rs`), moved into the per-bit counts every 255 pairs, instead of a branch per changed bit, and busy IDs are found in a 256-slot table of recent lookups before the hash map. The 1M-frame candump demo loads natively at 419 MB/s against 272 MB/s (240 against 149 when sorted after reading) and in wasm in 274 ms against 352 ms (423 against 575 sorted); the counts are the same bit for bit and memory after the load is unchanged (see README.md)
- [x] Plot queries: level-of-detail pyramids, so a query no longer scales linearly with the points in range: each series builds a min/max pyramid (runs of 8, 64, 512 ... points) on its first view averaging 32 or more points a bucket, about 1.1 MB per million points and freed with the series; the views are the same as a scan's. Series decoded during a running capture scan until it ends, and series out of order always scan
- [x] Plot queries: a bucket whose first value is NaN (a float signal's NaN bit pattern, say) kept only that point, hiding the bucket's minimum and maximum, and a NaN later in a bucket was dropped. A decimated bucket now keeps its first NaN plus the minimum and maximum of its other values, in time order (up to 3 points). The pyramid keeps a sorted list of where each run of NaN values starts (4 bytes per run), and its views still equal a scan's bit for bit
- [x] Plot: a NaN as the first point in view left the y axis without a range (uPlot's `getMinMax` starts from the first non-null value, and NaN is not null), and elsewhere the line bridged NaN points. The Plot and Trace plots and Reverse Engineer's references now hand uPlot null for NaN and infinite values, only when a view has one, so the line breaks there and the y range fits the other values; the minimap and sparklines break their lines too, and readouts and Reverse Engineer's window stats show NaN instead of a NaN range
